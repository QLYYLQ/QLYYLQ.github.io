# 数据构建可能性指南（精简版）

2026-10-27。完整版是同目录的《数据构建可能性指南》，这里只留结论、做法和要你定的事，每节末尾注明完整版的对应章节，术语见完整版附 A。依据是 spectragent main（`380060f`）的 runbook、`lookahead/README.md`、`configs/lookahead/`、导出和 lookahead 的代码、轮次记录（`.agents/skills/af-project-history/references/lookahead-rounds.md`），之前的四份报告，以及 LAR 原文（arXiv 2605.18597v3）。脚本在 `数据构建可能性指南_notes/`（下称 `_notes/`）。

*标注：**论文报告**是论文里能核对的；**项目数据**是仓库文档、配置、代码或你实跑里的数；**本文实测**是这次我自己跑出来的；**推断**是由证据推出的；**直觉**是没有直接证据的判断；**建议**是具体做法。*

## 结论

1. **一轮怎么采已经定了，下一轮在当前 main 上、换快网络重录。** 照 runbook 的“配置指南 101”和 `configs/lookahead/` 跑。10 月 25 日原始录制全删了，10 月 24–25 日的改动也改了 teacher 的提示词（**项目数据**）。导出有四个坑，靠改导出配置和一个后处理脚本解决，脚本已经写好。
2. **数据分五族，计数单位不同**：A 录制轨迹按保留轨迹和监督步，B、C 分叉按可用决定（judge 判为合理、且执行符合意图），D 前瞻观察按 transition，E 人工按条、留出评测按站点和任务（**推断**）。
3. **扩量卡在任务和站点上。** 推荐档要 ≥6,000 个任务、≥100 个站点（数据量估算的**直觉**），上一轮是 15 个任务、5 个站点。自己写的任务文件能被框架列出（**本文实测**，没有真录），模板任务和“variants 变成新 live 任务”都能接进录制。
4. **分叉不适合凑 SFT 的量。** 每次决定的 token 和录制的一步差不多（约 1.4–1.6 万），10 月 24 日那轮按意图执行的同任务分叉只占 30%，换任务 50%；折到每个可用决定，换任务分叉约为录制的 1.8 倍，同任务约 2.5 倍（**推断**）。分叉只做只有它能做的：同一状态多个决定、换任务、反事实对。
5. **LAR 论文存在，NeurIPS 2026 录用没查到。** arXiv 2605.18597，ICLR 2026 MemAgents workshop 的 poster。latent action 是高频 n-gram 片段加新词表符号，用 KL 蒸馏学；输入都是文本或 HTML，Mind2Web 上 Qwen3-8B 的动作 token 只少 2.9%（**论文报告**）。
6. **照搬到浏览器动作上省得很少。** click 15 个 token 里 9 个是语法，坐标才是决定，压不掉（**本文实测**）。语法和整行宏全换掉，每步省 25–80 ms；少一次 `wait()` 省 1 秒，少一次模型调用约省 1 秒（**推断**）。
7. **把 LAR“缩短有效步数”换成缩短调用次数**（我的延伸，**推断**）：给多动作 chunk 打盲操作标签，把能合并的相邻步合成长 chunk，把转移类型做成 `<predict>` 里的离散 token。先用两个脚本量出比例再定。

## 1. 要什么数据

| 族 | 数据 | 训什么 | 来源 | 计数 |
|---|---|---|---|---|
| A | 录制轨迹 | 策略 SFT 主体 | `spectragent bench` 录制 | 保留轨迹、监督步，按步筛 |
| B | 同任务分叉 | 决定稳不稳、偏好对 | `branch_same_task.yaml` | 可用决定 |
| C | 换任务分叉 | 任务条件化（设计文档数据④） | `variants` 加 `branch_task_variants.yaml` | 可用决定 |
| D | 前瞻 transition | `<predict>` | 录制的帧、DOM/AX、落定记录、动作效果；`extract` | transition，失败轨迹也算 |
| E | 人工、留出评测 | 校准 judge、金标、泛化 | 三类审核队列加 `spectragent view` | 条；站点 × 任务 |

录制时 `browser.frames`（每个动作前一帧、观测后约 1 秒一帧）、`browser.dom_raw` 和 `recording` 四项都要开着，D 和 latent action 的数据事后补不回来。磁盘约每步 4.5 MB。（完整版第 2 节）

## 2. 一轮怎么采

命令照 `lookahead/README.md` 的 “A collection round”，完整版第 3.2 节抄了一份带注释的。顺序是：每个站点一个 sweep 录制，一台机器同时最多 3 个站点，每个 sweep 设 `--token-limit`（按每个任务约 60 万给）；跑 `health` 写排除文件；`variants` 写换任务的变体；跑三组分叉；`extract`、`stability`、`judge-forks`、`gold-queue` 建审核队列；`spectragent view` 标注；最后导出。录完一定翻截图，健康检查认不出风控拦截页。

导出的四个坑（**项目数据**，读了导出代码和 runbook）：

1. 发布配置的 `exclude_restoration_diverged: true` 和 `max_document_misses: 0` 多半会把分叉整条排除。**建议**导出时放开，再用 `_notes/export_postprocess.py` 只留 judge 两个回答都是 yes 的分叉。
2. 导出器不读健康检查的排除文件，坏录制会进训练集。同一个脚本的 `--exclusions` 把它们丢掉。
3. `split.by: site` 按完整主机名切，variants 任务从子域名深链接出发，同一个站会跨进 train 和 validation。**建议**用 `split.by: task`，跨站泛化交给留出站点；留出站点用 `exclude_sites` 写注册域名，按后缀匹配，能盖住子域名。
4. 整条打包在外部做（`export_postprocess.py --pack`）。按每条 20 步、13 个监督步估，训练 token 约为按步展开的 1/7，29 步时约 1/10（**推断**）。

这个脚本在 fixture 演练的真实导出上跑通了，排除名单和 judge 结果是我手写的（**本文实测**）。下一轮顺手比：`pace: recorded_timeline` 对 `recorded_llm_latency`（看各站点可评判比例）；`wait_actions: drop_when_capped` 配真的改写模型。（完整版第 3 节）

## 3. 成本和扩量

10 月 24 日那轮（**项目数据**）：15 个任务，330 个分叉，可评判 229（69%），只补站点规则重跑后 246（75%）；共 1,168 万 token。媒体区域规则让腾讯视频的可评判分叉从 0 到 40/70。同任务分叉上，规则和 judge 只一致 58%，judge 要先拿人工审核核对。

三档折成采集资源（**推断**；要录的步 = 保留轨迹 × 录制系数 1.3 × 20 步，每步 1.4 万 token、16.7 秒、4.5 MB，每台机器 3 个站点全天跑；耗时和磁盘用的是中位数，实际会更多）：

| | 最低档 | 推荐档 | 扩展档 |
|---|---|---|---|
| 保留轨迹 / 要录的步 | 1 万 / 26 万 | 3 万 / 78 万 | 10 万+ / 260 万 |
| teacher 输入 token | 约 36 亿 | 约 109 亿 | 约 364 亿 |
| worker 时 / 机器日 | 1,200 / 17 | 3,600 / 50 | 12,000 / 170 |
| 磁盘 | 1.2 TB | 3.5 TB | 12 TB |

步数是最大的变数：上一轮 L1 任务每条约 28 步，首轮约 29 步。任务都这么长的话，要录的步、worker 时、机器日和磁盘都要乘约 1.45（**推断**）。表里只算了录制，不含分叉、评判和推理输出。

任务来源按成本排：现成基准（`lexbench_browser`、`online_mind2web`、`browsecomp`，评测要用的写进去污染名单）；每站模板任务（必填 `task_id`、`task_text`、`start_url`，放在单独的数据根下，每个站点一个 split，录制时用 `--subset` 选）；`variants_to_tasks.py` 把 variants 变成从检查点 URL 出发的 live 任务，单独成一个 split；最后才是 Go-Browse 式的探索生成。站点分两类（**建议**）：广度站只录制，往 100 个以上扩；深度站录制加分叉，挑可评判比例高的页面族（门槛比如 ≥60%，**直觉**）。保留滚动、弹窗、键盘、拖动分层和多动作步。

节奏：试点重录 15 个任务加 5 个新站点，量每步 token、每条步数、步通过率、teacher 成功率；录到 1 万条保留轨迹训六次看学习曲线；还在涨再扩到 3 万。（完整版第 4、5 节）

## 4. Latent action

LAR 的问题（**论文报告**加我的判断）：没有在原格式上同预算微调的对照；单次运行，表格之间有对不上的数；换太多片段会突然崩，没给阈值。

浏览器动作实测（**本文实测**，Qwen BPE）：click 15（参数 6），type 19，scroll 7，hotkey 8，drag 29，wait 4。同一个点击，Qwen 的 computer_use 工具调用约 34，UI-TARS 15，紧凑写法 10。只换语法时，thought 60 token 的一步输出少 12–17%；thought 实际多长还没量。

四件事，按先后（**推断**、**直觉**）：

| | 做什么 | 用到的数据 |
|---|---|---|
| ① 审计 | 在导出上跑 `action_token_audit.py`，量 thought、语法、参数各占多少；宏符号省不到 20% 就不改词表 | 导出的 `train.jsonl` |
| ② 盲操作标签 | 多动作 chunk 里，后面的动作对着的屏幕变没变：动作前那一帧和 O_t 在动作点周围是否一致、有没有导航或滚动、命中元素是否相同 | 动作前帧、动作效果、DOM |
| ③ 合并步 | 把能合并的相邻步合成一个更长的 chunk（离线合并，或分叉时用 `prompt_contribution` hook 让 teacher 自己多发），和②一起用 | 同上，加改写模型 |
| ④ 转移类型 token | 跳页、原地更新、弹窗、滚动露出等做成离散 token 并进 `<predict>`，P1 里做有无对照 | 设计文档数据② |

`chunk_candidates.py` 在 `steps.jsonl` 上做②③里不用看图的那部分，报的是上限；像素和 DOM 核对还没写。推理端不用训练就能做的：约束解码的 jump-forward 把确定的语法一次填上，同时保证动作能解析。（完整版第 6 节）

## 5. 开工清单

1. 准备机器、快网络，固定宿主外观；在新网络上先录一两个任务，看截断时主文档没加载完的采集是否接近 0。第一批任务：上一轮的 15 个 L1 任务直接用 LexBench，5 个新站点各写 10 个模板任务（每站一个 split），`--list` 核对。
2. 录制，跑 `health`，翻截图。
3. 跑 `variants` 和三组分叉，同一批分叉上比两种 `pace`。
4. 建审核队列：稳定性队列默认 60 条；分叉判定先标 51 条左右；金标 `--n 100`，先标 calibration 那一半。分叉判定标完先算人和 judge 的一致率，再决定能不能用 judge 筛分叉。
5. 导出三份，每份只改一个变量；对要用的那份跑 `export_postprocess.py`，再跑审计脚本和 `chunk_candidates.py`。
6. 用试点的四个数更新数据量估算，再定录多少；把 variants 变成下一轮的 live 任务。

（完整版第 7 节）

## 6. 需要你定的事

| 决定 | 我的建议 | 理由 |
|---|---|---|
| 任务生成器先做哪种 | 每站模板任务，加 variants 变 live 任务 | 成本最低，格式已实测能加载 |
| 站点怎么分工 | 广度站只录制，深度站才分叉 | 分叉恢复率靠站点规则，每个新站补规则成本高 |
| 分叉怎么导出 | 放开两项筛选，外部按 judge 筛 | 发布配置多半整条排除分叉 |
| 验证集怎么切 | `split.by: task`，跨站看留出站点 | 按主机名切会让深链接任务跨进两边 |
| latent action 先做哪项 | ①审计和②盲操作标签，再决定③合并步 | 都不花新采集，先量比例 |
| 金标谁来标 | 还没定 | 标注流程要完整走一遍 |
| 下一轮 teacher 走哪条 API 路由 | 还没定（runbook） | 影响限流和复现 |
