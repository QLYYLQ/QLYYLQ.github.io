# Phase 1 protocol — 2026-09-23

## The behavior being tested

The user wants a CU/BU training method that exploits the phenomenon that an agent may anticipate useful regions of the next screen from its current session. Example: having searched product A, it searches product B and anticipates where the next result information will appear. We first establish a data recipe and measure starting checkpoints; we do not require a causal interpretation of any tag or hidden state.

For transition t -> t+1, prediction receives task instruction, observations no later than t, and the issued action/list at t. It outputs a ranked selection on an 8x8 normalized grid. The true screen t+1 is withheld until observation selection. Offline labels may use its action element box at t+1, but model-facing prediction inputs may not contain that box, action, DOM, URL or screenshot.

The runtime observation boundary decides where prediction is placed. A click, text entry or focus change can all matter; a hand-written list of "page-changing" actions cannot reliably decide the boundary.

The current observation `O_t` is already part of the session. In the user's example, it can still show product A's result layout while the agent issues a search for product B. Using `O_t` itself as the layout reference is fully within the intended research scope. The arm named `cold` in existing request IDs is therefore **current-only**, not a condition with no session or layout information. Both arms share `O_t` and `A_t`; warm-minus-cold measures the marginal value of additional, earlier history. A zero or negative difference does not refute next-observation patch prediction, and a useful current-position-copy policy is a legitimate starting behavior rather than a disqualifying result.

## Primary experiments

1. **Layout judge calibration.** Use Qwen3-VL-8B-Instruct and Qwen3-VL-32B-Instruct as the primary paired-screenshot judges, with Qwen2.5-VL-7B/32B as compatibility or architecture comparisons and UI-TARS-1.5-7B as a GUI-specialized comparison. Output `same_layout`, `different_layout`, or `uncertain`, where sameness means reusable visible spatial arrangement, not merely a shared page template. Include same-layout changed-content positives, exact revisits as a separate stratum, modal/scroll/responsive changes and similar-content different-layout negatives. Compare geometry/structure baselines. URL and structure labels are silver, not human ground truth. Export a blinded review set; report silver agreement rather than claiming calibrated human accuracy without review.
2. **Pre-observation spatial prediction, with an earlier-history diagnostic.** Measure region selection before the target observation using the current observation and issued action, with or without additional history. For the narrower earlier-history diagnostic, use the same target transition for warm/current-only comparisons and require an earlier analogous screen strictly earlier than t to survive in the warm prompt (`reference_in_window=true`). Report other history conditions separately; a reference outside the prompt window does not support a claim about earlier-history use. The current-only arm removes all earlier history, so the difference measures their marginal value and does not isolate a layout-specific mechanism. Include current-position-copy, earlier-position-copy and matched unrelated-history baselines to measure practical behavior; exceeding every simple baseline is not a causal-proof requirement. Keep prompt budgets and target transitions comparable; log any remaining history-length differences. Candidate discovery may use future labels offline, but do not reveal target-derived retrieval/oracle hints in the prompt. If a historical reference was selected using the future target's layout, disclose that offline oracle selection in metadata and interpretation.
3. **Full-target next-click agreement diagnostic and restricted observation.** With the same warm history and current observation, show the resulting full target screen and ask for the next click under the original task. Score agreement with the recorded next-click target. This is a full-observation task/grounding diagnostic, not a strict grounding upper bound: the task can admit multiple valid actions and the recorded trajectory can be imperfect. Separately, continue the actual prediction conversation with its generated output, expose only the selected target regions, and request `<check>` plus an action or `<revisit>`. A revisit continues that same conversation and adds only the newly requested regions. Preserve earlier observations and responses throughout, and never introduce the full target screenshot into the restricted branch. A missing target box is not definitive proof of insufficient information; labels based on this rule are visibility proxies. Count all observations/tokens and distinguish replay action agreement from online task success.

Use available 7/8B and 32B Instruct checkpoints as starting models. Protocol markers initially remain ordinary text tokens; do not mutate vocabulary for a zero-shot experiment or claim newly initialized special tokens already have learned meaning.

The action at t is supplied from the recorded trajectory in this pilot. Results therefore concern next-observation prediction given an issued action, rather than an autonomous end-to-end agent. Keep model/run/prompt lineage separate across prediction, check and revisit; do not silently combine one model's predicted regions with another model's continuation and call the result a single-model policy.

## Data recipe

- Prioritize already downloaded OpenHands WebArena task trajectories for task-conditioned prediction and bbox labels. Decode observations/actions chronologically; reject mismatched/offscreen boxes and missing screenshots.
- BrowserGym element IDs in strings such as `click('638')` are opaque on raw screenshots without visible Set-of-Mark labels. Resolve each issued action using only its pre-action observation: attach the normalized element bbox/point and, when available, its current AX role/name. Historical actions use their own pre-action observations. Keep the original action string as provenance; never use the post-action/target observation to explain an issued action to the predictor. Record or exclude unresolved ID-based actions so a null result cannot be attributed to an uninterpretable action encoding.
- Use GUI-Xplore screenshots and XML/state structures for mobile layout pairs. Its exploration actions lack reliable task goals; do not turn them into primary task-conditioned prediction labels.
- Add GUI-Odyssey real instructed mobile trajectories when extraction and action-coordinate checks are feasible. Use actual image dimensions, not unreliable orientation metadata.
- Keep raw inputs immutable. Derived records include dataset revision, source task/app/session, step indices, image paths and hashes, layout label provenance, target-box provenance, quality flags and split.
- Split by session/task, and where feasible app/template; never randomly split pairs that share screenshots. Fit thresholds and priors only on train/calibration groups.
- Export initial SFT examples with history -> action -> predict and restricted observation -> check/revisit. Keep silver/visibility labels explicit and validation targets separate from training examples.
- The initial SFT subset requiring `reference_step < current.step` is an auditable branch for teaching use of older history, not the definition of all valid in-session training data. A later version may include `current-as-reference` cases as their own stratum, without changing the frozen first-run requests or treating current-layout reuse as out of scope.

## Measurements and visual review

Report valid JSON/coordinate rate, point-cell hit@k, target-box area coverage@k, actual selected area, warm-minus-cold paired differences and session-clustered uncertainty. Give both the main reference-visible subset and all-history diagnostics, including transition/session/app counts. A box can overlap multiple cells: k/64 is a random baseline for point hit, not arbitrary box-overlap recall. Use exact or empirical matching random baselines for the latter. Report check/revisit coverage and skipped or malformed requests against the original eligible prediction set, alongside conditional continuation results, so output filtering cannot inflate the apparent end-to-end agreement rate.

Export ranked-grid overlays, history/current/withheld-target contact sheets, success/failure galleries, budget-vs-hit curves, and before/after-revisit examples. Attention to earlier visible frames can be an optional diagnostic, but attention computed after reading the target screen does not measure anticipation. Blacking out pixels does not itself reduce encoded token count; make cost claims only from measured crop/processor token counts and timings.

No fixed go/no-go threshold is inherited from the old proposal. A null zero-shot result can reflect elicitation, grounding, inadequate data or real limitations; distinguish these before recommending the next training experiment.

The primary functional evidence is the entire observable chain: choose useful regions before seeing the next screen, act using the resulting partial observation, request useful additional evidence when necessary, and measure the total visual/token/latency budget. Earlier-history gains are a diagnostic within that chain, not a mandatory condition for the user's idea to be viable. Keep functional success and efficiency separate: usable partial-observation behavior with no current speedup can still inform SFT, while a hit@k gain alone does not establish usable action or cost savings.
