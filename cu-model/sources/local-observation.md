## 结论

主张：小模型在长程网页任务上通过率更高。动机是上下文衰减，好的 CUA 不能靠 256K 到 1M 的上下文硬扛。界面是给人用的，版面一致、可预见，模型应当自己学会利用这一点，只看、只记会变的和跟任务有关的区域，于是上下文涨得慢、干扰少，决策更准；速度可能顺带变快，要实测。这个能力要训进参数，不靠外挂的 harness。predict 是主角；事后压缩历史只当对照；latent action 是次要模块，单独消融。

每一步怎么做：动作发出后、下一屏到达前，模型先写 predict，也就是一个或几个框（Qwen3-VL 原生的 0 到 1000 坐标）加上要找什么，读值的步骤再加一句应该看到什么。下一屏到了，只把框里的原图裁给它看，没有缩略图。它先写一个判定词（普通文字）：找到了，就接动作；没找到（页面对，东西不在框里），就补看，在同一张截图上再写一个框，最多整屏；不对（页面状态和期望不符），就纠正，比如返回、关弹窗、改搜索词、等加载。整屏也是合法的框，没见过的布局就选整屏；很抽象的交互页面，可能要连着整屏看几次才写得出小框。历史里只存模型自己选来看的区域，全部保留，不另设丢弃的规则。

证据（都是零样本，样本小，复核是模型做的，不是人标）：

- 下一步要看的地方确实可预见：把刚发动作位置附近的 8 格当预测，就能命中下一次点击 56/111；三个模型零样本只有 19 到 30。规律在，模型没学会用。
- 历史会干扰：LookAgain-8B 前瞻选格，只给当前屏 30/111，加同任务历史 19，加无关历史 13；两个 Qwen 掉得少，差距的区间跨 0。
- 给对区域，模型就能读对：连续矩形里要新看的字段读对 48/48。
- 框比固定切分看得少：证据包 13 例里，一个框装下证据，中位数只占 2.0% 屏幕；切 9 块或 16 块要选中 11% 到 12.5%，约是框的 6 倍。换成视觉 token，要看局部图怎么送：框往外对齐到 2×2 个 token 一格、按原尺寸送，3×3、4×4 用的 token 仍是框的 2.3 到 3.4 倍（逐例比值的中位数）；每块至少放大到 384×384 再送，中位数就一样了。
- 模型能写框：32B 零样本写下一屏的框，10 条格式全对，一半判对；8B 的错在坐标尺度和“不知道就给整屏”。先让模型分析布局再写框，四个模型里三个变差（只有 10 例）。

标签照 VW 的自监督：冻结的全细节 teacher 看着真实的下一屏，离线在细网格的候选块里找“只看这些，答案就和看整屏一样”的一组尽量小的块，外接框当 predict 的标签。找不到小区域、或者前缀推不出位置的步，标整屏。判定词的标签由 teacher 看整屏核对，没找到、不对的样本另外造（挪框、失败步、分叉、改 DOM）。格子和 Qwen3-VL 的视觉 token 对齐（一个 token 对应 32×32 像素），只在离线搜标签时用，模型见不到；模型写的框在裁图前往外对齐到 token 边界。

训练顺序：先做 SFT 和自监督（整屏底座，再做前瞻训练加 KL 自蒸馏），调好以后再上 RL，RL 的细节到那时再定。

主实验比四种做法：全保留历史、只留最近几步、事后压缩历史、本文方案，报通过率和用掉的上下文。本文方案要在上下文不多用的前提下，通过率高过事后压缩历史；只打平的话，它就只是另一种压缩。评测用 Odysseys 做主评测，WebChoreArena 做可复现的第二套，Online-Mind2Web 留出一部分网站做短任务对照。前瞻训练前，先在现有轨迹上测一次上下文衰减，步骤写在 todolist 里，你在自己的环境跑。

动作侧：LAR 式宏符号按我们的输出格式估，每步最多省 18.9% 的解码，约 38 毫秒，少一次调用却能省约 1 秒。所以 latent action 要省就省调用次数，把多步合成一个，先当消融做。

采集任务和底座数据：只用论文说的数据真能在 HF 或 GitHub 下到的来源。核了 12 个采集来源，过关的有五个：WebChain、AgentNet、WebSTAR 补整屏底座，InSTA 和 WebChain 的任务当采集种子；VeriWeb 和 Online-Mind2Web 的任务和网址也进采集。这些任务和网址不只照原样跑一遍：在不同的步上分叉、同一网址换任务，多造相似布局的数据，让同一模板反复出现。能下到的长任务只有 VeriWeb 的 302 个，所以长任务要拿种子自己串。

## 主张

论文要证明的是一种能力：小模型学会利用界面的可预见性管理自己的上下文，因此在长程任务上通过率更高。

上下文为什么是问题。10-28 试采平均每条轨迹 15.6 步，按导出格式每条有约 670 个 token 的固定部分，每步再加约 1,180 个，其中截图 880 个视觉 token，文字约 300 个；全历史到 15.6 步约 1.9 万 token，到 30 步约 3.6 万（**项目数据**，审查第 3.2 节）。Odysseys 上各模型平均用了 42 到 86 步（上限 100，**论文报告**），照同样的格式，100 步约 12 万 token。小模型在这么长的输入里会不会被干扰，还没在我们的任务上直接测过，“前瞻训练前先测”一节的上下文衰减测试就是测这个。

为什么能压。网页是给人用的：同一个站点版面固定，动作的结果大多出现在可以预料的地方。phase1 里两条简单规则就说明了这一点：抄刚发动作的位置，前 8 格命中下一次点击 56/111；在训练 case 上调出的一个常数点，命中要读的证据 17/23（**项目数据**）。

为什么要进参数。这条是你的取向：能力学进模型，不做成外挂。事后压缩历史属于外挂，模型本身没学到新东西。本文方案要模型自己决定看哪里、记什么，看的时候带着期望，看完先判定，不对就马上改。裁图、存历史仍由程序执行，但看哪里、留什么由模型决定；事后压缩历史里，这些由人写的规则决定。

省 token 本身不算贡献。按旧版的测算，事后压缩历史在第 30 步就能把上下文里的视觉 token 从 26,400 压到 11,436（前 29 张每张换成粗图加一块 384×384 局部图，约 364 个；当前一帧照看整屏，880 个，**推断**），不用学任何新能力。所以本文方案必须在通过率上赢它。

速度可能是附带的收益。现在每步目标输出约 50.8 个 token，其中 thought 约 28 个；页面落定的 p50 约 0.76 秒，少一次模型调用约省 1 秒（**项目数据**，审查和指南第 6.4 节）。要快，主要靠少看（prefill 的视觉 token 少）和少调用，压输出写法省不了多少。

这些证据合起来说明（**推断**）：

- 必须训练。版面的规律在，零样本的模型不会用，这正是论文要教的能力。
- 自监督有依据。模型拿着对的局部图能读对，所以“只看这些区域时答案和看整屏一样”可以当标签。这只在 14 个 case、公开数据上验过；BU 页面上的动作能不能也这样，由“只给对的区域时动作还对不对”那项测试回答。
- 框是合适的接口。它是模型本来就会的格式，大小能随需要变，也不会被格线切开；面积上比切分少看几倍，token 上省多少要看局部图按原尺寸送还是放大。格子留在离线搜标签时用。
- 每屏少推理有初步支持。先分析布局再写框，四个模型里三个变差（32B 从 5 升到 6），和你说的“不靠底座现场推理”一致，不过只有 10 例。
- 还缺的：上下文衰减在我们的长任务上有多大，没直接测过；phase1 的“历史会干扰”测的是选区，推不到通过率。

## 模型每一步怎么做

用一个例子讲。任务是“搜 iPhone 16，读第一个商品的价格”，模型刚在搜索框输入并按了回车。

- predict：下一屏还没到，模型写下要找的东西（需求类型，词表里的一个词）和框，框写成 x1 y1 x2 y2，几个框依次写，比如 `result_list 120 260 880 900`。读值的步骤再加一句应该看到什么，比如“含 iPhone 16 的商品和价格”。不知道下一屏长什么样（新站、没见过的模板、任务的第一步）就写整屏 `0 0 1000 1000`。
- 观察：下一屏落定后，只把框里的原图裁出来，接在同一个请求后面，每块前面写明它在全屏的坐标。裁之前把框往外对齐到视觉 token 的边界（缩放后截图上 32 像素的整数倍），见“标签从哪来”。没有缩略图。动作坐标一律用全屏的 0 到 1000，不用局部图里的坐标。
- 判定：模型先写一个判定词，用普通文字，不加特殊 token。找到了：要找的东西在框里，接着出动作，再写下一步的 predict。没找到：页面是预想的那一页，但东西不在框里，比如列表比预想的靠下，接着补看，在同一张截图上再写一个框，可以更大或换地方，最多整屏；补看之后再写一次判定词。不对：页面状态和期望不符，比如跳到了登录页、搜出来全是手机壳、还没加载完，接着纠正：返回、关弹窗、改搜索词、等待。纠正本身是动作，后面照常写下一步的 predict。
- 输出顺序：判定词、简短的 thought、动作（或补看的框），最后是下一步的 predict。
- 历史：只存模型自己选来看的区域和它写的文字（predict、判定词、thought、动作），全部保留，不另设丢弃的规则；记忆就是模型 predict 之后选来看的图（你 11 月 3 日说的）。新布局的第一屏模型多半选整屏；很抽象的交互页面，可能要连着整屏看几次才写得出小框。整屏看几次由模型自己定，标签那边，teacher 找到小区域之前都标整屏。后面同一模板的步就靠历史里看过的这些少看，这就是你说的“搜一次之后就感知到布局”。

几个实现上的细节：

- 输出长度（**本文实测**，`局部观察训练路线梳理_notes/predict_tokens.py`）：需求加一个框的紧凑写法 18 个 token，设计文档的 JSON 写法 31 个；判定词一两个 token。每步约多 20 个 token，每秒 250 个 token 时约 80 毫秒。
- 补看用的是同一张截图，不用再等页面落定，代价是多一次调用。
- 每个框裁成一块连续矩形，一步通常一两个框，接在同一个请求后面复用 KV。phase1 的受限观察链把每块各裁成小图、每次发新请求，平均每条 2.95 次调用，比一次整屏调用慢 5.9 倍，新增的视觉 token 平均 688 个，比 phase1 一张整屏（公开数据，分辨率低）的 481 个还多（**项目数据**）。原因多半是小图被处理器放大了（**推断**）：Qwen3-VL 的处理器默认每张图至少 65,536 像素（256×256，64 个 token），更小的图先放大到这个大小再切。
- 局部图按原尺寸送（**建议**）：框对齐到 token 边界以后，局部图里每个 token 看到的像素和整屏时完全一样，不用缩放；把处理器的最小像素调低（比如 32×32），小框就不会被放大。前提是小块局部图也能读对，要在“只给对的区域时动作还对不对”那项测试里，原尺寸和放大各做一遍。
- 局部图的位置编号（**直觉**，可选）：Qwen3-VL 给每个图像 token 编行号和列号（多维的旋转位置编码），单独送进去的局部图从自己的左上角重新数。框对齐到 token 以后，可以让局部图的 token 沿用它在整屏里的行列号，这样模型不只靠前面写的坐标文字知道这块在哪。没有证据，改的是模型内部，先当可选的消融。
- 上下文用量（**推断**，notes 里的 `token_floor.py` 和 `token_grid.py`）：整屏 880 个视觉 token。30 步里每步看一块区域、其中两次新布局看整屏，第 30 步的视觉 token：区域按原尺寸送，取按 2×2 一格对齐、还没收边的标签框（证据包上中位数 48 个，偏保守；收边到单个 token 是 33 个，第 30 步约 2,700）约 3,100；按处理器默认下限（64 个）约 3,550；照旧版每块至少放大到 384×384（144 个）约 5,800；区域都是四分之一屏（约 220 个，再大就标整屏）约 7,900。补看另算。事后压缩历史是 11,436，全留整屏是 26,400。关键是整屏看几次：按这四种区域大小，30 步里整屏看的步分别不超过 12、11、9、7 步，本文方案就不比事后压缩历史多。Odysseys 每个任务至少跨两个站，抽象页面也可能要连着整屏看几次，区域大小和整屏次数都要在主实验里报实际值。
- 要专门测的风险：预期之外的变化出现在所选区域外面（比如别处弹出对话框），模型这一步看不到，只能靠下一步的期望落空发现。机制分析里要统计这种变化漏了多少、晚几步才发现。

## 标签从哪来：照 VW 的自监督

VW 的做法是让冻结的全细节模型当 teacher，学生看压缩过的输入，学 teacher 的回答。放到我们这里，teacher 是整屏底座训完以后、冻结的同一个模型，它看整屏；学生只看自己选的区域。

区域标签（**建议**）：

- 对录下的每一步，teacher 看着真实的下一屏，先出一次整屏下的动作（读值步还有读出的值）。只在它和录下的动作一致时造区域标签，不一致的步标整屏。
- 在一张细网格上找候选块。候选从三处来：下一步动作目标元素的框（录制里有 DOM 和无障碍树，即 AX 的信息），thought 或答案里读到的值所在的 DOM 文本节点，答题时注意力最集中的几格（旧版里 LookZoom 的做法，便宜，可以先粗筛）。
- 从这些块出发往外贪心地加，每加一次，把选中的块合成连续矩形给 teacher 看，直到它出的动作和看整屏时一致；也可以用两边回复分布的 KL 小于阈值来判，和 VW 增补的保真度探针一样。
- 贪心找到的那组块（不保证最小）按是否连在一起分组，每组的外接框是一个 predict 框，多数步只有一个框。能通过的组不止一组时都留着，每个 epoch 抽一组，这是 09-27 设计里 `acceptable_bundles` 的规矩。
- 不看新画面也能出对动作的步（比如连着输入），找到的组是空的；这类步本来就该合并进多动作步，见“动作侧”。
- 网格和视觉 token 对齐，这是你 11 月 3 日提的。Qwen3-VL 先把截图两边各调成 32 的整数倍，切成 16×16 像素的 patch，再把相邻 2×2 个 patch 合成一个视觉 token，所以一个 token 对应 32×32 像素；我们 1280×720 的截图被调成 1280×704，40×22 个 token，共 880 个，和试采导出的数一致（官方 `preprocessor_config.json`，见“来源与核验”）。对齐的单位取合并后的 token，不取 16 像素的 patch：一个 token 被切开，它的内容就变了。
- 格子多大（**建议**）：贪心搜索用 2×2 个 token 一格（64×64 像素，1280×704 上 20×11 格，和 16×16 差不多细），搜到以后四条边再按单个 token 往里收。把证据包 13 例的框放到 1280×704 上（**本文实测**，`token_grid.py`）：证据框中位数占屏幕 1.99%，约 17.5 个 token；往外对齐到单个 token 是 33 个，面积是证据框的 1.87 倍；对齐到 2×2 一格是 48 个，2.67 倍。11 月 1 日那版建议的 16×16 网格是 2.0 倍，但它的格线不落在 token 边界上。
- 截图尺寸：新采集可以直接把视口设成 32 的整数倍（比如 1280×704），省掉缩放；不改也行，裁图和搜格子都在缩放后的 1280×704 上做（**建议**）。

整屏标签：加到预算上限（比如屏幕的四分之一，**直觉**，参照 phase1 补看时累计不超过 25% 的设置）还过不了，就标整屏。另一种情况是前缀推不出位置：历史里没出现过同一模板（按 URL 模式或版面聚类判断，做法见设计文档）的第一屏，也标整屏。09-27 设计里已经有“前缀能否预测”的分层，找不到窄区域的步保留成宽区域，正好对应“不认识就看整屏”。

要找什么：只写需求类型，按规则从录制里打，依据是下一步动作目标元素的类型，或者 thought 里读的字段。词表沿用设计文档的：result_list、status_feedback、form_field、nav_target、error_msg、dialog、page_body、unknown。

应该看到什么：只在读值的步骤写。teacher 看着下一屏写出能从前缀推出来的那部分（“含 iPhone 16 的商品”），不写具体的值；再过一遍泄漏检查，删掉前缀推不出来的内容，做法同 OmniReasoner 的后见合成加泄漏过滤（**建议**）。

判定词和后续动作的标签（**建议**）：

- 找到了：teacher 确认要找的东西在预测框里。
- 没找到：要找的东西在屏上别处。这类样本可以自己造：拿一个正确的步，把预测框挪开，给模型看错的区域，标没找到，再接正确的框当补看的标签。挪开的框只当输入，相当于上一步写错了框，不算损失；损失只算在判定词和补看的框上。不用新采数据。
- 不对：页面状态和期望不符。来源有三：录制里动作失败、跳到登录页或报错页的步；分叉里同一状态换了动作、结果不同的对；学 OmniReasoner 改 DOM 造，比如把结果页改成空结果或换掉商品。10-28 试采只有 24 个分叉，不够，下一轮要多做。
- 纠正：录制模型自己纠正过的步（返回、关弹窗、改搜索词）直接用；分叉里成功的那一支也能当纠正的目标。

自蒸馏的损失：VW 改的是输入，LAR 改的是输出，两者都是冻结的 teacher 加上在对得上的位置算 KL。我们也照这样：teacher 看整屏、用标准格式，学生只看所选区域，在 thought 和动作这些两边都有的位置上算 KL，学生看不到证据的地方照设计文档的规矩门控，这些位置不算 KL；predict、判定词这些 teacher 那边没有的输出，用上面的标签做交叉熵（**推断**）。

## 训练顺序

先做 SFT 和自监督，调好以后再上 RL（你 11 月 3 日定的）。

- 整屏底座：第一轮 SFT 照常用原图（你 10 月 29 日定的，原图留全分辨率）。它也是后面的 teacher。数据除了自己采的，可以加 AgentNet、WebChain 和 WebSTAR，动作统一换成全屏 0 到 1000 的坐标（**建议**，见“采集任务和底座数据”）。我倾向在这一轮里混进当前屏写框的样本，还没定（**建议**）。当前屏写框就是 11 月 1 日那版的“写框热身”，当时单列成一个阶段：在已经看得到的当前屏上，让模型按任务写出这一步要读或要点的地方的框，加上需求类型。比如任务是读第一个商品的价格，结果页已经在屏上，就框出那个价格。标签直接用录制里 DOM 元素的框，不用 teacher 去搜。它只练写框的格式和坐标尺度，不练预测：证据包里 8B 零样本写框，10 条里 7 条把坐标写成 0 到 1 的小数，3 条直接给整屏；phase1 里看得到时指认有 75% 到 81%，底子在。这类样本便宜，混进来就不用多一个阶段。
- 前瞻训练：整套协议一起训，predict、只看所选区域、判定词、动作或补看或纠正，历史只存看过的区域。数据是把采集到的轨迹按离线标签重新导出，再加上自己造的没找到样本。同时加自蒸馏的 KL。
- latent action 的消融在前瞻训练这一步并行做，见“动作侧”一节。
- RL：上面几步调好以后再做，细节到时候定。我现在的想法先留在这里（**建议**）：先做拒绝采样 SFT，在真实网页上跑串好的长任务，成功用种子自带的成功标准加 LLM judge 判；奖励只用长任务成功和格式，不给定位奖励（OmniReasoner 和设计文档都是这样，直接从基座做 RL 在 OmniReasoner 里比基座还低）。要防两种塌缩：总看整屏（安全但不压缩），从不补看。出现总看整屏时，再加一个只在成功回合才扣的上下文代价（思路同 DeepEyes 只在答对时才给的放大奖励）。

## 前瞻训练前先测的三件事

都用审查第 3.1 节那 30 条完整轨迹（约 470 步，审查建议你人工审的 100 步也从里面抽），从撞上人机验证那一步起，后面的步都去掉。这 30 条不进整屏底座的训练集。“只给对的区域”和规则基线两项有阈值或规则要调，轨迹按条对半分，一半用来调，另一半只报数；上下文衰减没有要调的，调提示用这 30 条以外的轨迹，30 条全拿来报数。

| 测试 | 做法 | 量什么 | 决定什么 |
|---|---|---|---|
| 上下文衰减 | 五种历史：全历史、最近 4 张截图、最近 2 张（更早的步只留文字）、只留文字、无历史。历史用录下的前缀，每一步在每种历史下各出一次动作。步骤、判一致的规则和分析写在 `局部观察训练路线梳理_notes/上下文衰减测试_todolist.md` | 和录下的动作的一致率，按步序看 | 靠后的步里全历史不如只留最近几张，就说明现有长度上已有衰减，论文的动机可以先立住；没有，就主要靠 Odysseys 这种更长的任务来证明 |
| 只给对的区域时动作还对不对 | 同一步给几种画面：整屏；只给 oracle 区域（下一步目标元素框和读值所在的 DOM 文本节点，对齐到 token 边界，裁成连续矩形），分三种送法：原尺寸，放大到至少 384×384，原尺寸往外扩到至少 384×384。整屏再采样一次，整屏对整屏的一致率当上限 | 动作一致率，读值步再比读出的值 | 只给对的区域时离上限差 0.15 以上（**直觉**），就先改裁剪的画法和区域定义，再去搜标签；原尺寸和另两种送法差不多，局部图就按原尺寸送 |
| 前瞻的规则基线 | 不用模型，算规则：抄刚发动作的位置、抄更早一步的、固定中心、按网站调出的常数区域、随机。真值分两种：下一步点中的元素框；读值所在的 DOM 文本节点 | 同面积下的覆盖率，按转移类型（规则从录制里打）和证据框大小分开报 | 训完的 predict 要在哪些转移上超过哪条规则 |

上下文衰减你按 todolist 在自己的环境跑：先拿零样本的 Qwen3-VL-8B 看方向，整屏底座训完再跑一遍为准；五种历史乘约 470 步，约 2,350 次调用，8B 上几小时以内（**推断**）。现有轨迹平均只有 15.6 步，更长的历史用 VeriWeb 的人工演示补测（平均 272.5 步）：全历史放不下（约 32 万 token），比的是只留最近 k 张截图时 k 取不同的值；前提是能按动作时间从录屏里切出每一步的截图，要先下载一条演示看格式（**推断**）。能分辨多大的差距（**推断**）：同一批步上配对比较，靠后的步有一两百个，设置之间有两成的步改变决定时，差值的 95% 区间约 ±0.1，更小的差距这次测不出来。

“只给对的区域”那项的样本量（**推断**）：470 步里点击步约 150 个（点击的一致与否最好判），报数的一半约 75 个，一个五成上下的比例 95% 置信区间约 ±0.11，所以差距小于 0.15 时别下结论（0.15 是**直觉**）。

## 主实验与评测

主表比四种做法，都从同一个整屏底座出发，用同样的轨迹和同样的训练流程（RL 上了以后，四行也都照同样的流程各做一遍），只换每步看什么、历史存什么；本文方案多出的挪框样本和 KL 算在方法里（**建议**）：

| 做法 | 每步看什么 | 历史里存什么 |
|---|---|---|
| 全保留历史 | 整屏 | 每一步的整屏 |
| 只留最近几步 | 整屏 | 最近 k 步的整屏（k 取 2 和 4），更早的只留文字 |
| 事后压缩历史 | 整屏 | 每张旧截图换成粗图加一块局部图（按出动作时注意力最集中的地方选） |
| 本文方案 | 自己选的区域，可以整屏 | 看过的区域 |

事后压缩历史那一行也要在压过的历史上训过，零样本直接压对它不公平。

每一行报：通过率（Odysseys 的全对率和细则平均分，WebChoreArena 的准确率）、每步和最后一步的视觉 token、每个任务的调用次数和墙钟时间。主张成立的条件：本文方案用的上下文不多于事后压缩历史，通过率比它高，以 Odysseys 的全对率为主。Odysseys 只有 200 题，通过率在 10% 上下时 95% 置信区间约 ±4 个百分点，差距小于这个数就要多跑几遍，或者结合 WebChoreArena 一起看（**推断**）。

评测集（**论文报告**，细节和出处在 `局部观察训练路线梳理_notes/eval_benchmarks_20261031.md`）：

- Odysseys（ICML 2026），主评测：200 个任务，由真实浏览会话改写，每个至少跨两个网站，在真实网页上跑；环境是 OSWorld 里的 Chrome，截图加坐标动作，和我们的形式一致；步数上限 100，各模型平均用 42 到 86 步。按细则打分，每题中位数 6 条，judge 和人工的一致性 κ 0.79 到 0.85。全对率：Opus 4.6 44.5%，Qwen-3.5-9B 13.5%，Qwen-3.5-35B-A3B 6.5%，UI-TARS-1.5-7B 1.0%。真实网页会变，四行要在同一时间段里交错跑。
- WebChoreArena，可复现的第二套：532 个任务，跑在 WebArena 的四个自建站点上；专门考记大量信息、计算和跨页面记住，正好对着上下文；步数上限 50。BrowserGym 加 Gemini 2.5 Pro 是 44.9%，同一框架在 WebArena 上是 59.2%。只有 12 个任务非看截图不可，多数靠文字也能做。
- Online-Mind2Web，短任务对照（你 11 月 3 日定的加进来）：300 个任务，来自 136 个网站，最难一档才 11 步以上，用来看压缩会不会伤到短任务，报任务成功率，用它自带的 WebJudge 或我们统一的 LLM judge 判。任务在 HF `osunlp/Online-Mind2Web`，同意条款、留下联系方式后能下，CC BY 4.0；每个任务只有网址、任务描述和人做完用的步数，没有轨迹（11 月 3 日查的）。你打算把它的网址和任务也用到采集里，进过采集的网站就不能再当评测，所以我倾向按网站留出约三分之一不采，对照只在这部分上报（**建议**）。

机制分析，也是论文里的图：

- 同一页面模板访问次数越多，模型选的区域是否越小。这是“测试时感知布局”最直接的证据。
- 判定词的准确率（对 teacher 的标签），以及判定为没找到、不对之后多少步内恢复。
- 所选区域外的变化漏了多少、晚几步发现。
- 训完的 predict 和规则基线的对比。

## 动作侧：latent action 放在哪

审计的数（**项目数据**，审查第 4 节）：每步目标输出约 50.8 个 token，thought 约 28 个，动作语法约 16 个，参数约 7 个。按我们的输出格式估，LAR 式宏符号最多省 18.9%，每步约 9.6 个 token，约 38 毫秒；页面落定 p50 约 0.76 秒，少一次调用约省 1 秒。所以宏符号压的那点解码不值得改词表，要快得靠少调用。

LAR 本身的证据也弱（**论文报告**）：它在 Mind2Web 上实测，Qwen3-8B 的动作 token 只少了 2.9%，比我们按格式估的上限低得多；也没和“同样预算在原格式上微调”比过，分不清提升来自新符号还是多训了一遍。不过它对 latent action 的定义，即引起同样状态转移的动作片段算一类，和本文方案对得上：一段合成的动作结尾是一个可预期的转移，predict 正好接着说去哪里验证它。

做法（**建议**）：保留多动作步（你定的）；导出时合并相邻步、打盲操作标签（指南第 6.4 节，`chunk_candidates.py` 已经写好不看图的那部分），先量可合并的步占多少；多步合成一次输出先用现有的文字格式，要不要换成一个新的 latent token，放在前瞻训练这一步做消融，比通过率、调用次数和墙钟时间。

这些来源的任务和网址都拿来多造数据，不只照原任务跑一遍（你 11 月 3 日定的）。做法（**建议**）：

- 在不同的步上分叉：从录下的某一步恢复同一页面状态，换一个动作或换一个任务接着跑。一条录制能长出好几条后续，前面经过的页面是同一批。
- 同一网址换任务：在同一个站、同一类页面上让 LLM 照页面内容出新任务，比如同一个商品列表页，一次读价格，一次比评分，一次加筛选。
- 串长任务，见下面。

为什么值得做（**推断**）：predict 的小框标签只出现在同一模板在历史里出现过的步上，没见过的模板标整屏。同一个站、同一个模板来回出现得越多，“看过一次布局，后面少看”的样本越多，这正是论文要教的能力；同一页面换任务，还能让模型学到框跟着任务变，不只跟着布局变。机制分析里“同一模板访问越多、选的区域越小”那张图也靠这类数据。

代价：指南估过，一个能用的分叉决策约是一个录下来、能用的步的 1.8 到 2.5 倍（**项目数据**）。10-28 试采只做了 24 个分叉，恢复成功 18 个，太少，改不了这个倍数，下一轮要多做并量出来。

能下到的长任务只有 VeriWeb 一家，302 个不够训练，所以长任务要自己串（**建议**）：

- 种子：WebChain 的任务（人做完过）、InSTA 的任务（站点多），以及 Online-Mind2Web 和 VeriWeb 的任务。
- 串法：同站或跨站串 3 到 6 段，后一段要用前一段读到的值，比如先查出一个型号，再去另一个站比价，逼模型记住前面看过的东西。每段沿用种子自带的成功标准当判据。
- 过滤：从 Odysseys 放出的 `data/odysseys.json` 里抽出它用到的域名，采集任务和底座数据都避开这些站；Online-Mind2Web 留出做对照的网站、VeriWeb 留来测长历史的任务也不采，底座数据里这些站的轨迹也去掉。
- 先小规模试采，量串出来的任务实际多少步、录制模型能做完多少，再放量。粗算（**推断**）：WebChain 每条约 10 步，串 3 到 6 段约 30 到 60 步；InSTA 只有计划步骤，实际步数要试采才知道。

## 附：术语

| 术语 | 含义 |
|---|---|
| predict | 动作发出后、下一屏到达前，模型写下的框（一个或几个，0 到 1000 坐标）、要找的东西，读值步还有应该看到什么 |
| CUA、harness | CUA 是看屏幕、操作电脑或浏览器的 agent；harness 是模型外面的控制程序（裁图、管历史、调工具） |
| VW、LAR | VW 是 VisionWeave（arXiv 2610.07987）；LAR 是用 latent action 压动作输出的那篇（arXiv 2605.18597） |
| 前缀 | 这一步之前模型拿到的全部输入：任务、历史、当前看到的区域 |
| 多动作步 | 一次输出里连着几个动作，10-28 采集保留了这种格式 |
| 判定词 | 看到框里的内容以后写的一个词：找到了、没找到、不对 |
| 补看、纠正 | 判定为没找到时，在同一张截图上再写一个框看；判定为不对时，做纠正动作（返回、关弹窗、改搜索词、等待） |
| 整屏 | 框 `0 0 1000 1000`，看完整的下一屏 |
| 事后压缩历史 | 每步照常看整屏做决定，做完把这张截图换成粗图加一块局部图存进历史；旧版里已经提过 |
| 上下文衰减 | 输入越长，模型越容易被无关信息干扰，表现变差（context rot） |
| teacher 验证 | 冻结的全细节模型只看候选区域时，出的动作是否和它看整屏时一致 |
| 整屏底座 | 第一轮用原图做的全量 SFT；后面当 teacher |
| AX | 无障碍树（accessibility tree）：浏览器给每个元素记的角色、名字和位置，录制里和 DOM 一起存 |
| 当前屏写框 | 在已经看得到的当前屏上，写出这一步要读或要点的地方的框和需求类型，标签用 DOM 框；只练写框的格式和坐标尺度，倾向混进整屏底座一起训。11 月 1 日那版叫写框热身 |
| 视觉 token、patch | Qwen3-VL 把截图切成 16×16 像素的 patch，相邻 2×2 个 patch 合成一个视觉 token 送进语言模型，所以一个 token 对应 32×32 像素；1280×704 的截图是 880 个 |
| 全历史、最近 k 张、只留文字、无历史 | 上下文衰减测试里的几种历史：截图全留；只留最近 k 步的截图，更早的步只留文字；历史里不留截图；只给任务和当前屏 |
| phase1 | 9 月 23 日起的零样本定位测试：111 条公开数据转移（web 80 条来自 OpenHands、BrowserGym，手机 31 条来自 GUI-Odyssey），另有 97 条显式定位；模型是 Qwen3-VL-8B、32B，10 月补了 LookAgain-8B 和 UI-TARS-1.5-7B |
| 显式定位 | 给整屏和一句写明要找哪个控件的话，看点是否落在控件框里 |
| 前 8 格命中 | 下一屏到达前，模型在 8×8 的格子上排出前 8 格，看下一次点击框的中心在不在里面；随机期望是 8/64 |
| 只给当前屏、带同任务历史、带无关历史 | 前瞻测试的三种历史设置，项目文件里叫 current-only、warm、unrelated |
| 抄动作、常数点 | 位置规则：取刚发动作的位置；在 8 个训练 case 上调出的一个固定点，在 14 个证据 case 的 23 个字段上命中 17 |
| E2 | 9 月 29 日的读取实验：14 个证据 case（13 个有要新看的字段，共 24 个，其中 23 个有框）、两种历史设置，所以每个模型每种画面 48 个字段；只换模型看到的画面，单轮读，不许补看 |
| 证据包、seed10 | 11 月 1 日导出的 `cu_model_evidence_basemodels_20261101.zip`，13 例 23 个字段就是 E2 里那 23 个有框的字段；seed10 是包里 10 个 case、两种提示、四个模型零样本写下一屏框（1 到 3 个）的结果，带模型复核 |
| 09-27 设计 | 9 月 27 日的方法决定：predict 输出 0 到 1000 的矩形列表，正标签存成可接受的几组（`acceptable_bundles`），按“前缀能否预测”分层，check（对验证结果的标注，对应这里的判定词）分几类标签 |
| 需求类型 | 要找的东西的类别：result_list、status_feedback、form_field、nav_target、error_msg、dialog、page_body、unknown（设计文档的词表） |
| 动作一致率 | 同一步上，比较的两种设置出的动作是否一致，用规则或 LLM judge 判 |
| 30 条轨迹、人工审的 100 步 | 审查建议从 10-28 那轮随机抽约 30 条完整轨迹（约 470 步）逐步审，你再从中抽 100 步人工审 |
| BU、spectragent | BU 是浏览器里的任务（browser use）；spectragent 是项目录轨迹、做分叉用的采集框架 |
| 分叉 | 从录制的某一步恢复同一页面状态，换一个动作或任务再跑 |
| 录制模型 | 10-28 那轮录轨迹时做决定的模型 `deepseek-v4.1-flash-m17`，看全分辨率截图 |
| 宏符号、latent action | LAR 把引起同样状态转移的动作片段归成一类，用一个符号表示；宏符号是它的一种实现，把常见的动作片段换成新词 |
| 合并步、盲操作标签 | 合并步：把能连着执行的相邻两步合成一步；盲操作标签：标出多动作步里后面的动作能不能不看新画面就执行（指南第 6.4 节） |
| Odysseys、WebChoreArena、Online-Mind2Web | 三个网页 agent 评测集，Online-Mind2Web 只当短任务对照，见“主实验与评测”一节 |
| WebChain、AgentNet、WebSTAR、InSTA、VeriWeb | 数据能下到的五个公开来源，见“采集任务和底座数据”一节；Online-Mind2Web 的任务和网址也进采集 |
